# PIN sign-in for the family

Family members join with the family PIN, their first name and their own 4-digit PIN, and sign in with their first name and PIN (birthday, and for older accounts last name, only when asked). No email.
Admins and invited members keep the email sign-in (small "Admins: sign in with email" link).

## How it works

- **Join** (one step at a time, each sliding in once the one before it is done): (1) the 6-digit **family PIN** (shared in the WhatsApp group), checked by the server as soon as six digits are typed (10 tries per IP per hour, taken before comparing); a right answer returns a **join ticket**, `<expiresAtMs>.<HMAC-SHA256("bff-join:" + SERVICE_ROLE_KEY, expiresAtMs ":" sha256(familyPin))>`, valid 30 minutes and bound to the current family PIN (a new family PIN voids every ticket in flight; an expired ticket sends the person back to step 1 with "please type the family PIN again"). (2) **First name**; "Next" asks the server, with the ticket, whether anyone already has a PIN account with that first name (same normaliser as sign-in; counted per IP; strangers without a ticket cannot ask). (3) **Birthday**, only if the first name is taken ("Someone with this first name has already joined. Add your birthday so we can tell you apart."); first name + birthday may not match an existing account. (4) **Own 4-digit PIN twice**, then "Join the family". Last name is no longer asked for. The join action re-checks the ticket and the name rules itself (never trusting the browser), creates the account server-side (`auth.admin.createUser`, placeholder address `m-<uuid>@members.bigfatfamilytree.com.au`, `email_confirm: true`) with `name_key` = the normalised first name and the birthday if given, waits for admin approval, signs the member in straight away and sends them to `/welcome`. At most 5 accounts are created per IP per hour (`pinJoin`, fail closed), since a ticket can be reused for 30 minutes. A race with someone joining under the same name at the same moment is caught by the unique indexes and answered with the birthday step (or "duplicate").
- **Members without a birthday** (their first name was free when they joined): migration 29 allows a PIN account with no birthday and keeps at most one per `name_key` (`profiles_pin_identity_nobirthday_uidx`). Sign-in by first name finds them as usual. If a later member with the same first name joins (with a birthday), sign-in asks for the birthday; a birthday that matches nobody falls back to the one birthday-less account with that first name, so the original member can still sign in. That is no weaker than their own "first name + PIN": the PIN and that account's lockout still apply. Their lockout key uses an empty birthday, the same on every form. The first time the fallback signs someone in, the birthday they gave is saved to their profile (audited as `pin_birthday_added`; skipped if it would clash), so from then on that first name matches exact birthdays only and a namesake who mistypes their birthday can never reach this account.
- **Password**: never the PIN. `base64url(HMAC-SHA256("bff-pin:" + SUPABASE_SERVICE_ROLE_KEY, userId + ":" + pin))`. The PIN is stored nowhere. Rotating `SUPABASE_SERVICE_ROLE_KEY` would invalidate every PIN account's password (admins would have to reset each PIN), so do not rotate it casually.
- **Sign-in on a new device** (first name + PIN): the form shows First name and PIN, plus a small link "Not working? Add your birthday" that reveals the birthday dropdowns. The server (service role) normalises the first name with the same normaliser as `name_key` and compares it with every PIN account's normalised `first_name` (a list of a few hundred rows per attempt; no `first_key` column or migration was needed). Exactly one match: sign in to it. No match, or a birthday that does not match the unique account: the usual dummy attempt and the generic "Those details don't match". Two or more matches (the tree has several Samuels, Nassifs, Nabils, Rosas, Victorias): with no birthday the server answers `need_birthday` ("We need your birthday too, as more than one person has this name.") and the UI reveals the dropdowns; with a birthday it picks first name + birthday, and if that is still more than one person it answers `need_last_name` and the UI reveals the last-name field. `need_birthday` / `need_last_name` never try a PIN and never touch an account lockout, but do count against the first-name and IP limits, and take the same padded response time as every other path. Giving last name + birthday (the original form) still works and goes straight to the account.
- **Sign-in lookup**: the server finds the profile by `name_key` + `date_of_birth` + `login_method = 'pin'`, derives the password and calls `signInWithPassword` with the SSR client so session cookies are set normally. Every failure shows one generic message; response time is padded to at least 700 ms.
- **Limits** (Upstash, fail closed for PINs): per normalised first name on the first-name form 20 tries per 15 minutes and 50 per day, taken BEFORE the account is resolved (a first name alone is guessable; not reset by a correct PIN, and everyone called Samuel shares it; refusals use the same "too many tries" messages); per account 5 tries per 15 minutes and 10 tries per 24 hours (taken before each attempt, atomically, and cleared by a correct PIN or an admin reset; the 24-hour lock writes a `pin_locked_24h` audit entry); 20 sign-in attempts per IP per 15 minutes; 10 wrong family PINs per IP per hour.
- **Reset PIN** (admins, `/admin/members`): random non-trivial 4-digit temporary PIN shown once; sets `profiles.pin_must_change`; member sees a banner and `/account/pin` ("Change my PIN" in the user menu). A reset also clears the lockout. Admins can reset non-admins; only the super admin can reset an admin.
- **Family PIN card** (super admin): current PIN, Copy, "Make a new family PIN" (only affects new joins), and a ready-to-paste WhatsApp message. The first PIN is generated automatically on first read.

- **Switch an email account to a PIN** (user menu > "Sign in with a PIN instead", `/account/pin/setup`): first/last name and birthday (prefilled) plus a new PIN twice. Server-only, always the caller's own id. Requires an email account whose sign-in is under 24 hours old (otherwise: sign out and use an email link; chosen over asking for the email password because magic-link admins have none). Order: (1) `auth.admin.updateUserById` sets the derived password and `app_metadata.login = 'pin'` + `name_key`, real email untouched; (2) the profile is updated through the service role (`login_method`, names, `name_key`, `date_of_birth`, `pin_must_change = false`). If step 2 fails (including the duplicate-identity unique-index race) step 1 is rolled back: metadata restored, password set to random bytes. The email password stops working; magic link and forgot-password still do, because the email is real.
- **PIN account that forgot its PIN** (only with a real email): `/account/pin` > "Set a new one with an email link" (same `/account/pin/setup` page). Needs a session started by an email link (magic link or reset link) within 15 minutes (checked from the JWT `amr` claim; a PIN sign-in does not count). Name and birthday stay as they are.
- `/update-password` redirects PIN accounts to `/account/pin`, so an email password cannot replace the PIN-derived one by accident.

## Remember this device (returning members type only their PIN)

- **New device**: first name + PIN (see above); the birthday (three dropdowns: day / month / year) and last name are asked for only when the first name is shared.
- **After any successful PIN sign-in or join** the server issues a random 32-byte token in the `bff_device` cookie (**httpOnly, SameSite=Lax, Secure in production, 1 year, refreshed on each use**) and stores only its **SHA-256** in `pin_devices` (migration 27: `profile_id`, `token_hash`, `created_at`, `last_used_at`, `user_agent_hint` such as "iPhone Safari"; no IP address). RLS is on with no policies and all privileges are revoked from anon/authenticated, so only the service role can touch it. The cookie never holds a name, birthday or profile id, and nothing JavaScript can read does.
- **Returning device**: `/login` is rendered on the server, which reads the cookie, looks the hash up and shows "Welcome back, <first name>" with an initials avatar and a 4-digit PIN field only. The server action resolves the profile from the token, then runs the SAME checks as the full form: per-IP limit, then the atomic per-account lockout (`takeAttempt`, `pinFail` / `pinFailDay`) keyed on the resolved profile's `name_key` + birthday. The full form uses that same key, so **the two forms share one counter** (5 tries / 15 minutes and 10 / 24 hours in total, however they are split). Same generic error text and 700 ms floor.
- **Unknown, revoked or expired token** (unused for over a year): the cookie is cleared silently and the full form is shown. **"Not you?"** deletes this device's row and the cookie, then shows the full form.
- **Revoked** (all of that member's rows deleted, audited as `pin_devices_revoked` with a count, never a token) when an admin resets the PIN, the member changes their PIN (this device is then remembered again), or an email account sets/resets a PIN at `/account/pin/setup`. Deleting the account cascades. **Signing out** deletes only the current device's row and cookie. At most **10 devices per member**; the least recently used is evicted. Remembering a device is audited as `pin_device_remembered`.
- Security note: the token alone signs nobody in. The PIN is still required, and the lockout above still applies. A stolen phone with a live cookie only lowers the bar from "name + birthday + PIN" to "PIN", which is why the lockout is shared and a PIN reset or change kills every remembered device.

## Supabase dashboard settings (owner action)

1. **Authentication > Sign In / Providers > Email**: keep **Enable Email provider** and **Allow password sign in** ON. PIN accounts are ordinary password accounts to Supabase. "Confirm email" can stay on (PIN accounts are created already confirmed).
2. **Authentication > Sessions** (stay signed in about 90 days): leave **"Time-box user sessions" off** and **"Inactivity timeout" off** (both are Pro-plan options; on the free plan sessions already never expire). If either is on, set it to **90 days or more**. The refresh token is what keeps people signed in. Our session cookie (`lib/supabase/cookie-options.ts`, 90 days) is **rolling**: the middleware rewrites it with a fresh 90 days whenever it refreshes the 1-hour access token, so it expires only after 90 days without a visit. (`@supabase/ssr` would otherwise use 400 days.) Even then, a remembered device only needs its PIN.
3. **Authentication > Rate limits**: the "sign-ups and sign-ins" limit is per IP and shared by everyone on one home network; the default (30 per 5 minutes) is fine for a family.
4. JWT expiry can stay at the default 1 hour: the access token refreshes silently.
5. Apply migration `20260523000026_pin_login.sql` BEFORE deploying this code (the members page selects the new columns), then `20260524000027_pin_devices.sql` (remember this device). Without migration 27 the login page still works (the device lookup fails soft and shows the full form) but nothing is remembered.
6. Apply `20260530000029_pin_join_first_name.sql` BEFORE deploying the step-by-step join. Without it, joining without a birthday is refused by the database (the old check constraint and trigger require a last name and birthday).
